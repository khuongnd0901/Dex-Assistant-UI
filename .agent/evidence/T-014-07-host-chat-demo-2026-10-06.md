## Runnable host flow

1. Backend: `./mvnw -q -Dtest=ChatDemoFixtureServerTest -Ddex.chat.demo.fixture=true test`.
   Wait for `CHAT_DEMO_FIXTURE_READY`; the current source serves for five
   minutes. The passing run on 2026-10-06 used a three-minute hold and
   returned exit 0; the hold was extended afterward for reproducibility.
   The fixture answers by retained pair count:
   “Bây giờ là 7 giờ sáng.”, “Buổi sáng, bé An gặp một chú chim ở vườn.”,
   then “Chú chim dẫn bé An đến cây táo.” It delays the exact cancellation
   prompt by 300 ms.
2. Android host: set `DEX_CHAT_DEMO_WS` to that endpoint and
   `DEX_CHAT_DEMO_TOKEN` to the fixture token, then run
   `./gradlew :app:testDebugUnitTest --tests '*ChatLiveDemoTest*' --max-workers=1 --offline`
   under JDK17. Focused run PASS 1/1. XML retained at
   `/tmp/T-014-07-android-live-demo.xml` with correlated session/request IDs,
   all three exact replies and injected TTS completion markers.
3. The Android client used Chat start/turn/end frames over the live socket.
   Replies had one session ID, request correlation and turns 1–3. `USER` end
   was acknowledged. A pending turn was cancelled on disconnect, never replayed,
   and a subsequent connect started a different session. No Command action or
   protocol-error callback fired. A prior run reached all three replies but
   the immediate reconnect received `CHAT_SESSION_LIMIT` while server close
   propagation was in flight. The passing demo waits 800 ms after disconnect;
   this is a demo-only timing workaround, not a deterministic reconnect claim.
