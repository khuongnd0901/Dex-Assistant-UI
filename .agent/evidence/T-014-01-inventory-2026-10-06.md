## Identity, privacy, and implementation constraints

- Authentication proves possession of the shared configured bearer credential,
  not a distinct installation/user. The handshake sets one constant `deviceId`;
  do not bind Chat sessions to an installation identity unless auth is changed
  and that contract is explicitly reviewed.
- Current Command backend context is process-memory state keyed by a client ID;
  current Android Command history is encrypted local persistence. Both are
  unsuitable for Chat reuse under the accepted session-only/no-transcript policy.
- Provider calls already pass through `MeteredPlannerProxy` in the inspected
  configured provider path. The existing response adapter is tool-oriented, and
  its usage is unknown; source inspection cannot establish actual provider-side
  token billing or retention. Keep provider, quota, timeout, and data-policy
  decisions open pending the next policy task.
- The existing voice pipeline releases app-owned KWS capture before handing
  off to system STT. This does not prove selected Fold3/Bluetooth route behavior
  or real TTS echo rejection; those remain physical acceptance questions.
