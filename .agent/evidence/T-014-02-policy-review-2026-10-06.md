## Accepted v1 context and message bounds — owner approval 2026-10-06

| Bound | Concrete proposal | Meaning / enforcement |
| --- | --- | --- |
| Context | At most 20 complete user/assistant pairs and 8,000 input tokens for the complete prompt (system/time context, retained pairs and new turn), whichever binds first; evict only whole oldest pairs. | A pair means one user turn plus its assistant reply. Count the assembled prompt with the selected model's tokenizer; evict oldest complete pairs to remain under both bounds. |
| Input | At most 2,000 Unicode code points of recognized user text per turn. | A code point is a Unicode text value; accented letters and emoji can contain multiple code points. Count code points, not UTF-8 bytes or model tokens. |
| Output | At most 1,024 generated tokens or 4,000 Unicode code points, whichever limit is reached first. | Tokens are provider/model-specific units; code points are Unicode text values. Enforce the token output option and validate returned text. |
| Provider/account budget | Single owner-approved provider for v1; Chat shares its already configured admission, provider/model and request/token budgets. Add no provider fallback, quota, model, timeout, or spend without approval. Do not enable paid calls until both input/output token ceilings and a currency spend cap are configured. | Check actual deployment tier/model/budget outside source control; enforce request/token reservations in the metered proxy; emit usage counters only, never text. Existing 2 RPM example is test-only. |
| Sensitive text/privacy | Explain that final STT text and bounded context leave device for the selected provider; send no raw audio, screen, contacts or Command history. Reject known credentials/payment-card patterns using a shared validator; state clearly this cannot detect every sensitive fact. Never log/store prompts or replies. | Synthetic marker scan of app/backend logs/files/history; focused rejection tests; UI disclosure. Provider-side retention remains separate. |
| Provider error/retry | Failed, cancelled, expired and late turns add no user/assistant pair; no automatic provider retry initiated by Android. A transient error can leave the session active until idle expiry; end/auth/policy errors close it. | Fake-provider failure and cancellation tests; retry identity cannot invoke generation twice. Exact codes belong to T-014-03. |

An 8,000-token context limit is only meaningful if included prompt components are
counted for the selected model. A request budget without token/output or monetary
limits cannot substantiate a no-cost-increase claim. A configured local reservation
also cannot establish the external provider's actual tier or account quota.

## Final owner decision

On 2026-10-06 the owner agreed to all three explained content limits: 20
retained user/assistant pairs and 8,000 total prompt input tokens; 2,000 Unicode
code points of recognized input per turn; and assistant output capped at 1,024
generated tokens or 4,000 Unicode code points, whichever is reached first.
Together with the lifecycle/concurrency values above, the T-014-02 decisions
are complete. Provider-policy review remains explicitly out of scope. Keep the
current Gemini-through-proxy path and $0/month target; no paid fallback or
integration change is authorized.
